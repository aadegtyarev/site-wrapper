# Code quality

Status: active. Applies to all application code, tests, build scripts, and future platform modules.

## Boundary and consumers

This contract governs how contributors implement and review code in this repository. Product behavior is defined by the relevant feature and surface contracts.

## Maintainability rules

- Prefer the smallest clear implementation that satisfies the contract. Remove duplication, dead code, unused dependencies, speculative abstractions, and unnecessary configuration.
- Keep modules cohesive: one clear responsibility per module, narrow public interfaces, explicit dependencies, and no hidden cross-module state. Split a module when its responsibilities diverge; do not split it only to meet a line-count target.
- Choose names that state domain meaning. Keep data flow and control flow easy to follow. Avoid clever shortcuts that save lines at the cost of readability.
- Preserve platform boundaries: shared rules belong in testable core code; Firefox, Windows/Linux, and Android adapters own their platform APIs. Define and test data or protocol boundaries used by more than one component.
- Handle errors at a useful boundary. Return or report failures with context; never silently discard them. User-facing recovery follows the [UX contract](ux.md). Do not log passwords, tokens, or URL credentials.
- Pin dependencies and keep them current through deliberate updates. New dependencies need a concrete benefit over existing code or standard libraries.

## Comments and prose

- Code should explain *what* through names and structure. Add a comment for *why*: a non-obvious invariant, security constraint, platform quirk, or deliberate tradeoff.
- Do not add comments that restate the adjacent code, ornamental section banners, boilerplate summaries, or autogenerated-sounding filler. Delete stale comments when behavior changes.
- Keep documentation factual and specific to this project. Avoid vague promises, repeated descriptions, and promotional or AI-style filler.

## Verification and review

- Tests cover observable behavior, contract boundaries, and meaningful failure cases. Avoid tests that merely repeat the implementation or lock in private details.
- Formatting, static checks, tests, and builds must pass in the project container or CI before a change is considered verified. Add a regression test for a defect when it captures a real failure mode.
- Review each change for unnecessary complexity, module boundaries, error handling, security-sensitive data, and consistency with the affected contracts.
- When a check cannot run on the current platform, state exactly what remains unverified; do not claim production readiness from a cross-build alone.

## Non-goals

- Fixed limits on file length, function length, comment count, or test count.
- Abstraction or test coverage for its own sake.
